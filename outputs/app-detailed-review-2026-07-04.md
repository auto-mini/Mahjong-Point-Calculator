# 리치마작 부수계산 앱 상세 리뷰 기록

검토 기준: 모바일 390px 폭 실제 렌더링, 도메인 계산 로직, 공유/최근기록 복원, 입력 정규화, 기본 보안 위험.

## 선조치한 명백 오류

1. 순서가 섞인 슌쯔가 `unknown`으로 판정될 수 있었다.
   - 영향: 공유/최근기록/향후 수정 경로에서 `m2,m1,m3` 같은 순서가 들어오면 유효한 슌쯔가 버려질 수 있음.
   - 조치: 숫자를 정렬한 뒤 최솟값 기준 연속성으로 판정.

2. 부수로 만관이 되는 3판 70부, 4판 40부 등의 `limitName`이 비어 있었다.
   - 영향: 점수는 만관으로 계산되지만 결과 표시/최근기록의 역명 표시가 일관되지 않음.
   - 조치: 기본점이 2000 이상이면 `만관`으로 표기.

3. 마지막 깡 직후 판정에서 UI와 도메인 검증이 불일치했다.
   - 영향: 손패에 깡쯔가 없고 `마지막 깡 직후`만 true인 상태에서 UI는 통과시킬 수 있는데 결과 계산이 뒤늦게 막힐 수 있음.
   - 조치: 손패에 판단 가능한 깡쯔가 없으면 해당 깡도라를 인정하지 않는 쪽으로 도메인 검증을 UI와 맞춤.

4. 리치/더블리치를 끈 뒤 비활성 우라도라가 상태와 수량 검증에 남을 수 있었다.
   - 영향: 사용자는 우라 영역이 비활성이라고 보는데, 예전 우라 표시패 때문에 결과에서 수량 오류가 날 수 있음.
   - 조치: UI 정규화에서 비활성 우라를 제거하고, 도메인 수량 검증도 리치/더블리치일 때만 우라를 포함.

5. 론으로 4개 커쯔 중 하나를 완성한 샨퐁 형태를 사암각으로 오판할 수 있었다.
   - 영향: 실제로는 비역만인 손패가 `역만 손패`로 계산 불가 처리될 수 있음.
   - 조치: 사암각 판정에도 론 완성 커쯔의 암각 제외 규칙을 적용.

6. 조작된 공유/최근기록 상태에서 머리가 `open: true`로 들어올 수 있었다.
   - 영향: UI에서는 불가능한 후로 머리가 내부 분해에서 고정 몸통처럼 취급될 여지가 있음.
   - 조치: `createMeld`에서 머리는 항상 `open: false`로 정규화.

7. 만관 이상 최근기록/동점해석 라벨이 일부 경우 부수를 계속 표시할 수 있었다.
   - 영향: 부수로 만관이 된 경우 이전 요구사항의 “최근계산에는 몇 판만”과 어긋남.
   - 조치: `score.limitName`이 있으면 라벨은 `N판`만 표시.

## 검증 완료

- `node --test tests/domain.test.js`: 33개 통과.
- `node scripts/verify-static-app.js`: 통과.
- 실제 브라우저 390px 폭에서 확인:
  - 1페이지 본장 0~8 한 줄 유지.
  - 2페이지 37종 패 그리드가 만/통/삭/자 4줄로 유지되고 가로 넘침 없음.
  - B2 패 이미지 로딩 실패 없음.
  - 후보군은 머리/커쯔/깡쯔/슌쯔 줄 구분 유지, 슌쯔 후보는 한 줄에 2개 배치 가능.
  - 리치 상태에서는 후보 클릭 시 후로 O/X 없이 닫힌 세트로 바로 등록.
  - 3페이지 표시패 입력 칸은 선택된 칸 번호를 숨기고, 빈칸만 `+`와 번호를 표시.
  - 결과/최근계산에서 만관 이상은 부수 라벨을 숨김.

## 의견 확인 필요

1. 같은 탭에서 공유 URL의 `#s=` 해시만 바뀌면 앱 상태가 즉시 복원되지 않는다.
   - 현재는 최초 로드 때만 공유 해시를 읽는다.
   - 새 탭/새 로드 공유 링크는 정상 범주지만, 이미 열린 앱 주소창에 다른 공유 링크를 붙여넣는 경우까지 지원할지 결정 필요.

2. 깡이 포함된 완성 손패는 `현재 15장 / 완성가능`처럼 표시된다.
   - 내부적으로는 깡쯔 4장을 모두 입력하므로 맞지만, 사용자에게는 `깡 포함` 같은 보조 표기가 더 명확할 수 있음.

3. 동점 해석 후보 필터가 “같은 총점 + 같은 판수”만 보여준다.
   - 이전 요구가 “판수 동점 후보”라면 같은 판수지만 부수/점수가 다른 후보도 보여줘야 할 수 있음.
   - 반대로 현재처럼 실제 동점 점수만 보여주는 편이 더 조용함.

4. `panel(title, note, children)`의 `note` 인자가 현재 렌더링되지 않는다.
   - 숨겨진 설명을 의도한 흔적으로 보이지만, 설명 문구를 줄이자는 최근 방향과는 충돌할 수 있음.
   - 선택지: 인자를 제거해서 코드만 정리 / 접이식 설명으로 렌더링 / 현상 유지.

5. 3페이지 `확인 필요` 박스는 도라/우라 입력이 하나라도 있을 때만 보인다.
   - 장점: 초기 화면이 덜 시끄럽다.
   - 단점: 도라 첫 칸이나 마지막 깡 직후 질문을 아직 안 넣었을 때 버튼만 비활성이고 이유가 즉시 보이지 않을 수 있음.

6. 공유 해시 길이 제한이 없다.
   - 입력값은 allowlist로 정규화되고 HTML 삽입은 쓰지 않지만, 아주 큰 해시를 일부러 넣는 DoS성 링크는 방어가 약함.
   - 보안 하드닝으로 `decodeShareState`에 최대 길이 제한을 둘지 결정 필요.

7. 최근계산 중복 제거 기준이 `label`이다.
   - 같은 점수/판부/오야 여부면 서로 다른 손패가 하나로 합쳐질 수 있음.
   - 최근기록을 “계산 결과 목록”으로 볼지 “입력 상태 히스토리”로 볼지에 따라 결정 필요.

8. `stepper`, `shortTile` 같은 미사용 함수가 남아 있다.
   - 동작 버그는 아니지만 유지보수 관점에서는 삭제 후보.

9. 량페코 판정에서 같은 슌쯔 4개인 특수 케이스를 어떻게 볼지 룰 확인이 필요하다.
   - 현재 구현은 서로 다른 슌쯔 쌍 2종이 있을 때만 량페코가 된다.
   - `123/123/123/123/55` 같은 형태를 작혼이 량페코로 보는지 확인 후 결정하는 편이 안전함.
