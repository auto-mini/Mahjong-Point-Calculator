# 리치마작 부수계산 웹앱 MVP 구현 목표

## 목적

리치마작 부수계산 웹앱의 실제 MVP를 구현한다.

이번 작업 범위는 와이어프레임을 실제로 사용할 수 있는 정적 웹앱으로 옮기는 것이다. 사용자는 모바일에서 화료 정보, 손패, 화료패, 도라/우라 정보를 입력하고, 앱은 일반역, 도라, 부수, 점수를 자동 계산해 결과를 보여준다.

MVP는 "작탁에서 휴대폰으로 빠르게 확인할 수 있는 4인 리치마작 계산기"를 목표로 한다.

## 비목표

아래는 MVP 범위가 아니다.

- 배포.
- 백엔드.
- 계정.
- 서버 DB.
- 온라인 동기화.
- 삼마 지원.
- 국사무쌍 입력/점수 계산.
- 역만 점수 계산.
- 유국만관.
- 노텐 벌부.
- 쵼보.
- 책임지불.
- 다중 론.
- 로컬역.
- 작혼 공식 이미지, 상표, 에셋 복제.

역만은 점수 계산하지 않고, 감지 시 `역만 손패입니다. 부수 계산 대상이 아닙니다.`처럼 명확히 중단한다.

## 고정 UI 기준

- 모바일 우선.
- 기준 폭: iPhone 14/15 계열 390px.
- 폰트: Wanted Sans를 우선 사용한다.
- 패 스타일: B2 타일.
- 전체 디자인 톤: I Wallet Stack 기반.
- 배경: G처럼 연한 웜 그라데이션.
- 구역: K처럼 바깥 배경보다 진한 패널로 분리.
- 결과 카드: 붉은 카드 중심.
- 보조 카드/프레임: 딥그린 계열.
- G의 지저분한 선 장식은 사용하지 않는다.
- K의 장난감 같은 강한 노랑/토이 감성은 피한다.
- 하단 주요 진행 버튼은 한 손 사용을 고려해 화면 하단에서 찾기 쉽게 둔다.
- 화면이 길어지는 것은 허용하되, 각 단계의 입력 흐름이 끊겨 보이면 안 된다.

## 기술 기준

구현 전에 현재 레포 구조를 확인하고, 이미 선택된 프레임워크와 빌드 도구를 따른다.

새 프레임워크 도입은 피한다. 기존 프로젝트가 없거나 선택지가 열려 있으면 정적 웹앱으로 단순하게 구현한다.

기술 스택 결정 방식:

- 사용자가 별도 스택을 지정하지 않으면 레포 확인 후 결정한다.
- 이미 앱 프레임워크나 빌드 도구가 있으면 그것을 우선한다.
- 기존 앱 구조가 없으면 MVP 범위에 맞는 가장 단순한 정적 웹앱 구조를 선택한다.
- 새 의존성은 계산 정확성, 테스트 가능성, 또는 구현 유지보수성에 명확히 도움이 될 때만 추가한다.

권장 구조:

- 계산 도메인 로직은 UI와 분리한다.
- 패/도라/역/부수/점수 계산은 순수 함수 중심으로 작성한다.
- UI 상태와 계산 상태를 명확히 분리한다.
- URL fragment 공유 스키마는 allowlist 방식으로 파싱한다.
- localStorage 데이터는 신뢰하지 않고 항상 재검증한다.
- `eval`을 사용하지 않는다.
- 사용자 입력을 `innerHTML`로 삽입하지 않는다.
- 외부 CDN에 의존하지 않는다.

- 계산 도메인 코드.

- 최근계산 저장/복원.

## 화면 흐름

MVP는 와이어프레임의 1~4페이지 흐름을 따른다.

1. 화료/국 정보.
2. 손패 입력.
3. 도라/우라/깡 직후 판정.
4. 결과.

구현 방식은 실제 라우팅, 단일 페이지 내부 단계 전환, 탭/스텝 전환 중 레포에 가장 맞는 방식을 택한다. 사용자가 체감하는 흐름은 와이어프레임과 같아야 한다.

## 공통 내비게이션

- 1페이지에는 뒤로가기 없음.
- 2~4페이지 좌상단에는 뒤로가기 버튼.
- 2~4페이지 우상단에는 최근계산 버튼.
- 최하단 확인 버튼은 페이지별 필수 입력이 완료되어야 활성화된다.
- 확인 버튼은 화면 하단에서 찾기 쉬워야 한다.
- `다시 계산`은 전체 초기화 후 1페이지로 이동한다.
- 일부 수정은 뒤로가기로 처리한다.

## 1페이지: 화료/국 정보

필수 입력:

- 론/쯔모.

기본값:

- 장풍: 동.
- 자풍: 동.
- 본장: 0.
- 공탁: 앱 입력/결과에서는 제외하고 0으로 고정.
- 상황역: 해당없음.

상황역:

- 리치.
- 더블리치.
- 일발.
- 창깡.
- 영상개화.
- 해저로월.
- 하저로어.
- 해당없음.

상황역 제한:

- 해당없음은 다른 상황역과 배타적이다.
- 리치와 더블리치는 동시 선택 불가.
- 일발은 리치 또는 더블리치가 있을 때만 유효.
- 해저로월과 하저로어는 동시 선택 불가.
- 창깡과 영상개화는 동시 선택 불가.
- 해저로월은 쯔모 전용.
- 하저로어는 론 전용.
- 영상개화는 쯔모 전용.
- 창깡은 론 전용.
- 후로 손패에서는 리치, 더블리치, 일발이 불가하다.

## 2페이지: 손패 입력

사용자는 최종 완성형 전체를 입력한다.

- 일반 손: 최종 14장.
- 깡 포함 손: 14장 + 선언된 깡 수.
- 화료패는 최종 입력 안에 포함된 패 중 하나를 별도 지정한다.
- 화료패를 별도 추가 패처럼 입력하지 않는다.

패 선택:

- 처음에는 37종 패를 모두 이미지로 보여준다.
- 37종: 만수 1~9, 통수 1~9, 삭수 1~9, 적5만, 적5통, 적5삭, 동, 남, 서, 북, 백, 발, 중.
- 패 하나를 선택하면 해당 패를 포함할 수 있는 후보만 보여준다.
- 선택을 취소하면 37종 전체 상태로 돌아간다.

후보 종류:

- 머리.
- 슌쯔.
- 커쯔.
- 깡쯔.

후보 동작:

- 머리는 후로여부 없이 선택 즉시 등록한다.
- 몸통 후보는 후로여부 O/X를 선택해 등록한다.
- O는 후로, X는 비후로로 처리한다.
- 깡쯔 O는 명깡, 깡쯔 X는 암깡으로 처리한다.
- 등록 후 후보군은 사라지고 패 선택 영역은 37종 전체로 돌아간다.
- 각 세트는 현재 손패 영역에서 묶음으로 표시하고 제거할 수 있어야 한다.

화료패:

- 손패 구성이 완성된 뒤 노출한다.
- 후보는 현재 손패 안의 중복 제거된 패로 제시한다.
- 적5와 일반 5는 구분한다.
- 같은 패가 여러 장 있으면 대표 1개만 후보로 보여준다.
- 화료패 선택 후 해당 패 1개만 강조 표시한다.

## 3페이지: 도라/우라/깡 직후 판정

상단 순서:

1. `마지막 깡 직후에 화료했나요?`
2. 예/아니오 선택.
3. 필요하면 추가 질문.
4. 판정 문구 출력.
5. 도라 표시패 입력.
6. 우라도라 표시패 입력.

도라 표시패:

- 5칸.
- 첫 칸 필수.
- 34종 일반 패만 선택한다.
- 적5는 표시패 타입으로 따로 다루지 않는다.
- 후반 칸이 비어 있는 것은 없는 것으로 자동 처리한다.
- 중간 칸이 비어 있으면 경고를 표시하고 결과 진행을 막는다.

우라도라 표시패:

- 리치 또는 더블리치가 없으면 비활성.
- 리치 또는 더블리치가 있으면 활성.
- 활성 상태에서는 우라도라 개수가 도라 표시패 개수와 같아야 한다.
- 개수가 맞지 않으면 경고를 표시하고 결과 진행을 막는다.

깡 직후 판정:

- 앱이 이미 알고 있는 화료 방식, 상황역, 손패의 깡 정보, 후로/암깡 정보를 바탕으로 마지막 깡도라/우라도라 인정 여부를 판단한다.
- 깡이 2개 이상이고 암깡과 암깡 아닌 깡이 섞여 있어 판단이 필요한 경우에만 추가 질문을 낸다.
- 리치/더블리치가 없으면 판정 문구는 도라만 언급한다.
- 리치/더블리치가 있으면 판정 문구는 도라와 우라도라를 언급한다.

## 4페이지: 결과

정상 계산 시:

- 최종 점수.
- 최종 몇 판 몇 부.
- 만관 이상 등급.
- 역 목록.
- 도라/우라도라.
- 부수 계산.
- 지불액.
- 본장 반영.
- 공유.
- 다시 계산.

계산 불가 시:

- 결과 영역 최상단에 `계산 불가`를 표시한다.
- 사용자가 고칠 수 있도록 이유를 구체적으로 표시한다.

역 표기:

- 역 이름과 판수를 줄마다 표시한다.
- 도라는 `도라 N`.
- 우라도라는 `우라도라 N`.
- 깡도라와 적도라는 별도 줄로 표시하지 않고 도라에 합산한다.
- 역패는 `동`, `남`, `서`, `북`, `백`, `발`, `중`처럼 실제 패 이름만 표시한다.
- 장풍과 자풍이 같으면 `더블동`, `더블남`, `더블서`, `더블북`처럼 표시한다.
- 후로 감산이 있어도 `후로 혼일색`처럼 표시하지 않고 `혼일색`으로 표시한다.

동점 후보:

- 최고 점수가 같은 후보가 여러 개여도 기본 결과는 하나만 표시한다.
- 판수까지 같은 후보가 있으면 아이콘을 표시한다.
- 아이콘을 탭하면 후보 목록 팝오버를 보여준다.
- 팝오버는 화면 밖으로 나가지 않아야 하며, 바깥 탭으로 닫혀야 한다.

## 계산 기준

기준 룰:

- 작혼 4인 일반게임/단위전 계열 룰.
- 쿠이탕 있음.
- 후로 감산 있음.
- 연풍패 머리는 4부.
- 핑후 쯔모는 20부.
- 치또이는 25부 고정.
- 절상만관 없음.
- 5판 이상은 부수 무관.
- 13판 이상은 카조에역만으로 표시.
- 적도라는 5만, 5통, 5삭 각 1장.
- 깡도라/깡우라도라 있음.
- 암깡 깡도라는 즉시 적용.
- 명깡/가깡 깡도라는 후공개 기준.

지원 화료형:

- 일반형: 4몸통 + 1머리.
- 치또이: 서로 다른 7종 또이쯔.

역만:

- 역만은 점수 계산하지 않는다.
- 명백한 역만 감지 시 계산을 중단한다.
- 국사무쌍은 입력 방식에서 제외한다.

지원 일반역은 `outputs/mvp-detailed-spec.md`의 일반역 판정 목록을 따른다.

## 부수 계산

일반형:

- 기본부 20.
- 멘젠 론 +10.
- 쯔모 +2.
- 핑후 쯔모는 20부 예외.
- 단기/간짱/변짱 +2.
- 양면/샤보 +0.
- 삼원패 머리 +2.
- 장풍패 머리 +2.
- 자풍패 머리 +2.
- 연풍패 머리 +4.
- 커쯔/깡쯔 부수는 요구패/중장패, 명/암에 따라 계산한다.
- 일반형은 합계 부수를 10단위 올림한다.

치또이:

- 항상 25부 고정.
- 10단위 올림하지 않는다.

5판 이상:

- 부수 계산이 결과 점수에 필요 없으므로 `부수 무관`으로 표시하고 세부 내역을 축약한다.

## 점수 계산

친/자:

- 자풍이 동이면 친.
- 자풍이 동이 아니면 자.

본장:

- 론: 기본 점수 + 본장 * 300.
- 쯔모: 각자 지불액에 본장 * 100 추가.
- 공탁은 앱 입력/결과에서 제외하고 0으로 고정한다.

등급:

- 5판: 만관.
- 6~7판: 하네만.
- 8~10판: 배만.
- 11~12판: 삼배만.
- 13판 이상: 카조에역만.

절상만관:

- 없음.
- 30부 4판, 60부 3판은 만관으로 올리지 않는다.

## 최근계산

- localStorage 기반.
- 최대 20개.
- 2~4페이지 우상단에서 열 수 있다.
- 전체 화면 모달 또는 하단 시트로 구현한다.
- 항목을 누르면 1~3페이지 입력값을 복원한다.
- 복원 후 4페이지 결과로 이동한다.
- 4페이지에서 뒤로가기로 수정 가능해야 한다.
- localStorage 데이터도 신뢰하지 않고 재검증한다.

## 공유

- 4페이지 하단에 공유 버튼을 둔다.
- 백엔드 없이 URL fragment 기반으로 현재 계산 상태를 공유한다.
- 최근 기록은 공유 링크에 포함하지 않는다.
- 실행 가능한 코드를 저장하지 않는다.
- 파싱 실패 시 `공유 링크를 읽을 수 없음`을 표시하고 빈 상태로 시작한다.

## 오류 상태

최소한 아래 오류를 UI와 테스트에 반영한다.

- 론/쯔모 미선택.
- 손패 미완성.
- 화료패 미선택.
- 동일패 5장 이상.
- 동일 수패 적5 2장 이상.
- 화료 형태 불가.
- 화료패가 최종 손패에 없음.
- 도라 첫 칸 누락.
- 도라 중간 칸 누락.
- 우라도라 개수 불일치.
- 도라만 있고 일반 역 없음.
- 후로 손패에서 리치/더블리치/일발 선택.
- 상황역 상충.
- 역만 형태 감지.
- 공유 링크 파싱 실패.
- localStorage 기록 복원 실패.

오류는 가능한 한 입력 구역 바로 아래에 표시한다. 계산 결과 단계에서 발견된 오류는 결과 영역 최상단에 표시한다.

## 구현 순서

구현 전략:

- 계산 엔진 최소 안정판을 먼저 만든다.
- 최소 안정판은 패 정규화, 수량 검증, 도라 순환, 일반형/치또이 기본 판정, 기본 부수/점수 계산, 대표 오류를 포함한다.
- 최소 안정판이 테스트로 검증된 뒤 대표 케이스를 확장한다.
- 대표 케이스 확장은 `테스트 추가 -> 구현 보강 -> 테스트 통과 -> 리뷰` 순서로 진행한다.
- 계산 엔진이 안정되기 전에는 UI 장식을 과하게 다듬지 않는다.
- UI는 초반부터 와이어프레임의 1~4페이지 정보 구조와 상태 흐름을 유지한다.

권장 순서:

1. 레포 구조와 실행 방법 확인.
2. 계산 도메인 모델 정의.
3. 패/도라 유틸 구현.
4. 화료형 분해 엔진 구현.
5. 역 판정 구현.
6. 부수 계산 구현.
7. 점수 계산 구현.
8. 도메인 단위 테스트 추가.
9. 입력 UI 구현.
10. 결과 UI 구현.
11. 최근계산 구현.
12. 공유 링크 구현.
13. 오류 상태 구현.
14. 모바일 시각 QA.
15. 자체 리뷰와 개선.

계산 로직이 안정되기 전에는 UI 장식을 과하게 다듬지 않는다. 다만 와이어프레임의 정보 구조와 모바일 흐름은 초반부터 유지한다.

## 작업 루프

1. 시작 전 `git status`를 확인한다.
2. 기준 문서를 끝까지 읽는다.
3. 현재 레포의 실행/테스트/빌드 방법을 확인한다.
4. 첫 MVP 구현 또는 다음 개선을 진행한다.
5. 가능한 테스트를 실행한다.
6. 가능한 빌드를 실행한다.
7. 모바일 390px 기준 화면을 확인한다.
8. 전체 자체 리뷰를 수행한다.
9. 개선할 점이 있으면 수정한다.
10. 실제 diff가 있으면 커밋한다.
11. diff가 없으면 커밋하지 않고 무개선 리뷰 카운트를 올린다.
12. 반복한다.

빈 커밋, 커밋을 만들기 위한 의미 없는 변경, 불필요한 포맷 변경 커밋은 금지한다.

테스트나 빌드를 실행할 수 없는 경우에는 이유를 자체 리뷰 기록에 남긴다.

## 중단 조건

아래 중 하나에 해당할 때만 중단한다.

- 사용자가 중지를 지시한다.
- 작업 시간이 10시간을 초과한다.
- 100번 리뷰 동안 개선할 것이 없다.

100번 리뷰 동안 개선할 것이 없으면 즉시 종료하지 말고 최종본 정리 산출물을 추가로 만든다.

## 100번 무개선 후 최종본 정리

100번 리뷰 동안 개선할 것이 없을 경우 아래 산출물을 추가한다.

- 최종 MVP 구현 요약 MD.
- 테스트 결과 요약 MD.
- 모바일 QA 요약 MD.
- 알려진 제한사항 MD.
- 다음 버전 후보 과제 MD.

필요하면 추가로 만든다.

- 390px 기준 최종 화면 스크린샷.
- 오류 상태 스크린샷.
- 최근계산/공유 흐름 스크린샷.
- UI 밀도 미세 조정 후보.

이 단계에서도 실제 파일 변경이 있을 때만 커밋한다.
